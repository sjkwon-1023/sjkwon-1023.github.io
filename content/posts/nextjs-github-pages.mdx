이 블로그는 Next.js 16 App Router로 만들어 정적 파일로 내보낸 뒤 GitHub Actions로
GitHub Pages에 배포한다. 설정 자체는 짧지만, 그 짧은 설정에 도달하기까지 **빌드는 통과하는데
결과물이 틀린** 종류의 문제를 여러 번 만났다. 기록해 둔다.

## 1. trailingSlash 를 켜지 않으면 슬래시 붙은 URL이 404가 된다

기본값(`trailingSlash: false`)으로 내보내면 글 하나가 이렇게 나온다.

```text
out/blog/hello.html
out/blog/hello.txt     # 클라이언트 내비게이션용 RSC 페이로드
```

그런데 GitHub Pages는 `/blog/hello/` 요청을 파일이 아니라 디렉터리로 해석한다. 디렉터리가
없으니 404다. 반대로 `trailingSlash: true` 로 두면 이렇게 바뀐다.

```text
out/blog/hello/index.html
out/404.html
```

이러면 `/blog/hello/` 는 그대로 서빙되고 `/blog/hello` 는 301로 슬래시가 붙는다. 어느 쪽으로
들어와도 깨지지 않는다. 취향 문제가 아니라 사실상 필수 설정이다.

대신 한 가지가 따라온다. canonical URL, sitemap의 `<loc>`, RSS의 `<link>` 를 전부 슬래시로
끝나게 맞춰야 한다. 안 그러면 301되는 주소를 스스로 정본이라고 광고하는 셈이 된다.

## 2. sitemap.ts 와 robots.ts 는 `force-static` 없이는 빌드가 깨진다

이건 문서에 없다. `app/sitemap.ts` 를 추가하고 빌드하면 이렇게 죽는다.

```text
Error: export const dynamic = "force-static"/export const revalidate not configured
on route "/sitemap.xml" with "output: export".
```

메타데이터 파일이 내부적으로 라우트 핸들러로 컴파일되는데, Next가 자동 생성하는 래퍼에는
정적 생성 지시어가 안 붙기 때문이다. 직접 붙여 주면 된다.

```ts
// src/app/sitemap.ts
export const dynamic = "force-static";
```

`robots.ts` 와 직접 만든 모든 `route.ts` (예: `rss.xml/route.ts`)에도 똑같이 필요하다.

## 3. metadataBase 를 빼먹으면 조용히 localhost가 배포된다

이건 빌드를 **막지 않는다**. 노란 경고 한 줄만 남기고 통과한다.

```text
⚠ metadataBase property in metadata export is not set ... using "http://localhost:3000"
```

그리고 배포된 HTML에는 이런 게 들어간다.

```html
<meta property="og:image" content="http://localhost:3000/og.png"/>
```

슬랙이나 X에 링크를 붙여 보기 전까지는 아무도 모른다. 루트 레이아웃에서 명시적으로 잡아 준다.

```ts
export const metadata: Metadata = {
  metadataBase: new URL("https://sjkwon-1023.github.io"),
};
```

## 4. Tailwind v4의 `dark:` 는 기본적으로 미디어 쿼리다

v4의 `dark` variant는 `@media (prefers-color-scheme: dark)` 로 컴파일된다. 미디어 쿼리는
사용자가 누른 토글로 덮을 수 없다. 그래서 테마 토글을 붙이면 **CSS 변수로 만든 색만 바뀌고
`dark:` 유틸리티는 그대로 남는** 반쪽짜리 전환이 된다.

`@custom-variant` 로 방향을 바꿔 준다.

```css
@import "tailwindcss";

@custom-variant dark (&:where([data-theme="dark"], [data-theme="dark"] *));
```

`:where()` 를 쓰는 게 중요하다. 특이도가 0이라 `dark:bg-x` 와 `bg-y` 가 동등한 무게로 남고
소스 순서대로 해결된다. `.dark &` 로 쓰면 dark 유틸리티가 특이도 싸움에서 이기기 시작한다.

같은 맥락으로 토큰을 Tailwind에 노출할 때 `@theme` 이 아니라 `@theme inline` 을 써야 한다.
`inline` 이 없으면 빌드 시점 값이 유틸리티에 박혀서, 테마를 바꿔도 색이 안 따라온다.

```css
@theme inline {
  --color-bg: var(--bg);
  --color-fg: var(--fg);
}
```

## 5. 테마 토글은 배경이 아니라 아이콘에서 깜빡인다

`<head>` 안에 파서를 막는 인라인 스크립트를 넣어 첫 페인트 전에 `data-theme` 을 확정하는 건
잘 알려진 패턴이다. 그런데 여기까지만 하면 배경은 안 깜빡이는데 **해/달 아이콘이 깜빡인다.**
아이콘을 `useState` 로 고르면 hydration이 끝날 때까지 틀린 아이콘이 보이기 때문이다.

해법은 간단하다. 두 아이콘을 모두 서버 HTML에 렌더하고 CSS로 하나를 숨긴다.

```css
[data-theme="dark"] .icon-light           { display: none; }
:root:not([data-theme="dark"]) .icon-dark { display: none; }
```

state도, effect도, `mounted` 가드도 없다. hydration 전에도 아이콘이 정확하다.

## 덤: `.nojekyll` 은 이제 필요 없다

브랜치 기반 Pages에서는 Jekyll이 `_next/` 같은 언더스코어 디렉터리를 통째로 무시해서
`.nojekyll` 이 필수였다. 하지만 배포 소스를 GitHub Actions로 두면 Jekyll이 아예 안 돈다.

게다가 `actions/upload-pages-artifact` 는 v4부터 dotfile을 기본 제외한다. 즉 `.nojekyll` 을
만들어도 아티팩트에 안 들어간다. 넣어 봐야 무해할 뿐 효과가 없으니, 그냥 빼는 게 맞다.
