On macOS, I worked with several coding agents side by side in cmux. After moving to a Windows
desktop, I could not find a lightweight tool that preserved the same workflow. Rather than
customize a general-purpose terminal emulator, I built a Windows terminal around only the features
I actually used. I still use it every day when developing on my desktop at home.

The project started as winmux. A same-category terminal with the same name already owned the
search results, and the `win-` prefix read as a limitation rather than a choice, so I renamed it
mast. Since then I have added per-tab agent status, phone remote control, a Git changes viewer, a
built-in browser tab, and Apple Silicon macOS support, and released v1.0.0 in September 2026.

## Seeing active and waiting states on one screen

Within a workspace, panes can be split horizontally or vertically, and each pane can contain
multiple tabs. A sidebar next to the terminal shows, for each workspace, whether its agents are
running, waiting for input, or finished, together with their latest message. When a workspace
holds several agents, the sidebar shows the most urgent tab, and a tab that starts waiting gets
its own badge and a Windows notification. The central benefit is that I do not need to open tabs
one by one to check results while several agents run concurrently.

The file explorer and the text and Markdown viewers I missed in cmux also open as tabs. They let
me read documents and output files in the same window while an agent works. Large files are
loaded in 512 KiB windows instead of all at once, keeping a single viewer from substantially
increasing the application's memory use. I later added a read-only Git changes viewer that shows
the files an agent changed as diffs, split into working and staged scopes, and a built-in browser
tab for checking the web pages an agent builds without leaving the window.

Agents use the same structure. Inside a terminal, `mast ls` finds the tabs in the same workspace
and `mast send` sends input to an agent or shell in another pane, so one agent can hand work to
another. With `mast browser`, an agent can inspect elements and screenshots in the built-in
browser tab, and click and type there.

## Tracking agent status per tab

Hooks for Claude Code, Codex, OpenCode, and Antigravity CLI emit OSC 777 tokens—`mast:running`,
`mast:needsInput`, and `mast:idle`—into terminal output. The Rust OSC scanner separates them from
ordinary output and applies the status to the corresponding tab. Standard notifications such as
OSC 9 update only the unread state and message, preventing other programs from overwriting
coding-agent status. This uses the existing PTY stream as the status channel without adding a
daemon, IPC server, or named pipe.

At first, status was stored once per workspace. Running several agents in practice showed the
flaw: one tab finishing overwrote another tab that was still running, and when a second tab
started waiting in a workspace already waiting for input, no notification arrived. I moved the
status to each tab and had the sidebar show the most urgent one. Status is never guessed from
screen contents or process names; only each agent's own hooks count as signals. Settings that
require the user's trust, such as Codex hooks, are never bypassed; the user approves them
directly.

The UI retains only the running, waiting-for-input, and finished states; raw terminal output is
not converted to JSON. The output hot path remains a byte stream, and only low-frequency events
such as state changes are sent to the UI layer.

## Following up from a phone when away from the desk

Agents wait for input at unpredictable moments. So that I can answer when I am not at my desk, a
phone on the same LAN can be paired by QR code to read terminal output, scroll a full-screen TUI,
and send input to an agent or an ordinary Bash shell. The phone renders the screen with a headless
xterm, showing the same content as the desktop.

![The mast interface — per-workspace status in the left sidebar, panes holding Claude Code, Codex, and the file explorer, and a phone on the right reading and typing into the same terminal](/media/mast/desktop-and-phone.png)

There are two connection modes. The original Local HTTP mode opens only when enabled in settings,
and is documented for use on a trusted home network only. The added Secure Remote mode has a
GitHub Pages HTTPS page connect directly to the PC over WebTransport. Because the PC holds only a
self-signed certificate issued for each pairing, the phone pins the certificate's SHA-256
fingerprint carried in the QR code and accepts that certificate alone. The listener is open only
while the QR code is shown, only one phone can connect at a time, and the certificate expires
after at most 14 days.

Neither mode uses a cloud relay. The QR code carries only the PC's LAN address; reaching it from
another network requires a path the user sets up, such as a VPN. The pairing dialog does check the
Windows Firewall rules and, if needed, adds the rule after a UAC prompt.

## Defining a WSL2-only boundary first

On Windows, opening a terminal always means launching `ConPTY → wsl.exe → login shell`.
PowerShell and CMD profiles are not supported. This is a deliberate product boundary matched to
my own environment, where coding agents and development tools run inside WSL2—not an unfinished
general-terminal feature. Rather than expand the number of supported shell combinations, I focused
on the core features I use every day: splits, tabs, workspace switching, and agent status.

On a PC where WSL was not ready, the app failed again on every launch. It now diagnoses WSL once at
startup, distinguishes causes such as WSL not being installed, no distribution, or a shell that
fails to start, and shows the install command, the official guide, and a Recheck button. The app
never installs WSL or restarts Windows on the user's behalf.

Global shortcuts use `Ctrl+Shift` and `Alt+Shift` combinations so the shell receives its standard
`Ctrl` inputs wherever possible. Terminal conventions are preserved as well: `Ctrl+C` copies only
when text is selected and otherwise passes SIGINT to the shell.

## Separating the UI from the terminal lifetime

A UI-framework-independent Rust core owns terminal sessions, flow control, OSC parsing, the
replay buffer, and layout state. Tauri v2 is a thin bridge between the host and the WebView, while
vanilla TypeScript and xterm.js render the interface.

Because of this boundary, a WebView reload used to reclaim memory does not terminate the PTY
session. The new UI can reattach to the current state and scrollback. When the application itself
is closed and reopened, it restores the saved workspace, split, and tab structure and each tab's
working directory, but launches fresh shells rather than pretending the former processes are still
alive. In a tab that was running an agent, a single `Up` recalls the Claude Code or Codex resume
command to continue the earlier conversation.

The same boundary carried over to macOS. Sharing the workspace, pane, and tab model and the
terminal, replay, OSC, and agent-status pipelines, and splitting out only the platform-specific
parts, I built a native Apple Silicon macOS source build that launches zsh or bash directly.

## Keeping it lightweight while distributing it directly

I set an initial memory target of 100 MB and an upper bound of 150 MB. The roughly 129 MB measured
on an x64 Windows 11 desktop exceeds the target but remains below the upper bound; I accepted that
trade-off for the first release. As features grew, I focused on keeping unused features from
costing anything. Viewer code and the Markdown parser load when first opened, and with every
automatic UI reset turned off, the watchdog thread is not created at all. A browser tab creates its
WebView only when first shown, and turning the feature off in settings creates none of its
resources. A soak test that creates and destroys a ConPTY session 500 times confirmed that handle
and thread counts do not grow.

Portable executables for x64 and ARM64 are currently available through
[GitHub Releases](https://github.com/sjkwon-1023/mast/releases). The app checks once per launch
whether a newer version exists and says so, but leaves downloading and replacing the executable to
the user.

The project includes unit and integration tests for the Rust core and UI tests for TypeScript. CI
runs `check` and Clippy for both Windows targets, along with frontend builds and tests and an audit
of the public Secure Remote bundle. On release tags, Windows runners build the x64 and ARM64
executables and attach them to GitHub Releases.

## Scope verified so far

I use and validate the x64 Windows 11 and WSL2 combination in daily work on my home desktop. The
ARM64 target's verified scope is currently limited to successful builds and static checks in CI; it
has not run on real hardware. On macOS, the Apple Silicon source build has passed its automated
tests and a hands-on check of the browser tab; hands-on verification of the remaining features and
a signed distributable are still outstanding. Memory figures have not been re-recorded since the
browser tab was added, and Tailscale connectivity remains follow-up work.

I use it every day in my own workflow, and when something gets in the way, I fix that problem
before adding features.
